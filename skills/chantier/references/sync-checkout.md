# Sync the checkout

Read before the first sync of a dev-mode session, by the session that syncs (the `SKILL.md` launch paragraph says who; `$CHANTIER`'s mode is set there). A sync runs at the session's start, at a batch's start and after a merge that changes `uv.lock`. Six steps:

1. Check, writing nothing: run `uv sync --locked --check --project "<plugin root>"` (the command inside the rule P10 prints for it) and read its exit: 0 is in sync, nothing to sync, stop here; 1 with uv's text "The environment is outdated" goes to step 2; any other exit is an ordinary sync failure, handled as below, never `sync pending` (a stale `uv.lock` also gives 1 with that text, and the real sync of step 3 then fails with its lock error, handled the same way).

2. Name the holders before syncing, on every system: list the processes that hold `<plugin root>/.venv` by the host's means (its reference, row "Name the holders of the checkout's environment").

3. With none, run `uv sync --locked --project "<plugin root>"`.

4. With any holder (a gate, a watcher, the board or hub, of any project or surface, this session's own included), or when the sync fails with os error 32 (a holder the listing missed, or one that started in between), never stop or kill a process and ask no one to: go on unsynced, saying `sync pending: held by <holders>` (each holder as `PID <n> <subcommand> <project>`, a server `$CHANTIER webui` started (`serve --stop-idle`, no `--seat`) as `PID <n> serve <project> (started by webui)`, or `an unlisted process` when the listing found none), and try again from step 1 at each next turn but a reload (`session-start.md`, "5. Reload": a reload runs no `uv sync`).

5. Still pending 3 minutes after its first try, tell the user once, naming the holders, that the sync waits for them (a `webui`-started server still listed is named with its stop command (`taskkill /PID <n> /T /F` on Windows, `kill <n>` elsewhere, as `serve`'s refusal prints it), for the user to run by hand: it has no seat, its idle stop does not come while this session's watcher stays subscribed, and chantier never stops it; in a batch as the **For you** item of `status-layout.md`; outside a batch one chat line, and at most one more, step 6's offer), then go on as in step 4.

6. Your own board and watcher, on your yes: at the first try, at or after those 3 minutes, where every listed holder is this session's own board or watcher, offer once per pending sync to stop them, stating the cost: the board and the surface's writer are off for all projects meanwhile, the hub too, unless another session's watcher takes it (off a planning surface there is no writer, and the cost names the board and the hub only, with the same "unless"). When that holds at the 3-minute message, the offer is in that message; when it first holds later (a gate held `.venv` at 3 minutes and has ended since), the offer is, in a batch, the **For you** item's new state, and outside a batch one more chat line, the only one after step 5's. No third line: if a gate or another holder appears after the offer, say nothing more; the offer stands for a later yes while the conditions hold. "First try" is a turn, not a timer: no sleep, no monitor, no wake for it. "Own" is the host row's evidence: own board, its command line holds `--seat <this session's id>` and this session's `serve --seat` did not print `board already running`; own watcher, a `watch` process with this project's `--project` while this session holds a running watcher task and the project's seat; anything else is not own (another session's board included, and a server `webui` started, whose command line holds no `--seat`: step 6 never offers to stop it). An own process is stopped by the host's stop of the background shell that holds it, never by `Stop-Process`, `taskkill`, `kill` or a PID. On the user's yes: stop the watcher and the board, list the holders again, sync only if none, then start the board and the watcher again whatever the result (`session-start-chief-of-staff.md`'s board start, and the watcher's printed command, as is); a holder still listed after the stop is no longer own (its shell is gone): it is waited on as in step 4, never killed, and the board's restart then meets `board already running`, passed on as is. The yes covers the restart: no second question. A failed sync is one line with uv's text. No offer while another holder is listed or a gate runs (listed, or shown by `$CHANTIER status`). No answer: the offer stands. A no: keep waiting as in step 4, do not ask again; in a batch the **For you** item then names the holders only, plus "a later yes still counts". An ordinary sync failure is, at the session's start, `startup-core.md`'s; at a batch's start or after a merge, one line to the user with uv's text, and you go on.
