# A remote command or a CI job that fails

- A remote command (`git fetch`, `gh`, `glab`) that fails with a forge server error (HTTP 5xx) or a network failure (no route, a reset or timed-out connection, a name that does not resolve) runs once more, at once, with no `sleep`. Before re-running a command that creates or moves something (`gh pr create`, `glab mr create`, `gh pr edit`), check whether the first attempt took effect (`gh pr list --head <branch>`, or the forge's equivalent) and do not run it again if it did. `note <cr> "infra re-run: <command>: <exact error>"`. A second failure the same way: `handback <cr> blocked infra: <command>: <exact error>` (the stack driver: `msg steering anomaly "<cr> infra: …"`).
- A refusal (HTTP 4xx, a denied permission, a protected branch, a failed lease) is no infrastructure failure: it keeps its own route (`blocked refused`, `help refused-push`), with no re-run.
- A CI job that fails on the infrastructure gets at most the re-runs of CI's `timing:` line (on Claude Code the `subagent` one; on Copilot your model family's, else `other models`; 1 by default, 0 none), each at the same head. A failure the CR does not touch that passes on a re-run is a flake: a `note` names the test, the run and the symptom, for the Chief of Staff to file. Re-runs used up and still red: `handback <cr> blocked infra: CI <job> red on the infrastructure after <n> re-runs`.
- No result after 3 hours on one head (a longer CI in the project's rules gives its own limit): stop waiting, `handback <cr> blocked infra: CI still running after 3 hours`.
