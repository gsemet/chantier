# The gaps of a ready-to-merge ask (part 1 of 2)

- A plain `ready-to-merge <cr> <link> gaps: ...` ask (or `pr-in-draft <cr> <link> on <base>: waits for <what> gaps: ...`): when you tell the user the PR is ready to merge, quote each gap of the ask next to the PR's link, in the user's language (the `handed back:` line carries the same gaps from the hand-back); with none, say nothing about gaps.
- In every mode a `ready-to-merge` ask is offered to the user as mergeable now, on its own, with its gaps (the release PR: the same message asks the post-merge word, `help release-chief`). A `pr-in-draft ... on <base>: waits for <cr>` ask is not: say it is a PR in draft, do not merge, and what it waits for.
- Where the project's rules ask a local run, the ask of each CR that owes the run, in a parallel or series batch, carries `local gate <cr> at <sha7>: ...`: quote it in the user's language before saying the PR can be merged. `passed`: say the local gate ran and passed at that head. `not run` or `failed` (a `deliver by` time): say the project's rule asks that gate at that head before the merge and it has not passed there; merging anyway is the user's choice, recorded as any merge (`order merged`), never questioned or refused.
- A `handed back:` line's `long gate` clause is what the record holds; the local run the rules owe comes from the Foreman's ask, which you add. When the ask and the line differ, the ask wins. Nothing in the line is judged.
