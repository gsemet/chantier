# A stack ready to merge (part 2 of 2)

- On any stack ask add one clause in their language: heavy CI ran at the top PR's head only; merging a PR below without heavy CI at its own head is their choice; it can be run on that head if they ask (a report's partial-stack line does not repeat this). A merge in the middle is recorded as any merge, never questioned or refused. On their word to run it, `order note <cr> "heavy CI: at its head"`; the Foreman passes it on, and its `heavy-ci <cr> <head7> green|red <checks>` ask is told to the user (red changes nothing by itself: they decide). The local-gate record: the last `gate` events of that CR at that full head in `events.jsonl` (`status` keeps `exempt: <rule>` for `--no-gate`).
- A refused `$CHANTIER forge-stack rebuild` (an `anomaly`): the user gets the exact text; on their yes run the command the refusal's last line names (`forge-stack create` after `... is dissolved and no stack replaces it yet`, `forge-stack show` after `... the stack's state is unknown`), else `forge-stack rebuild`; no raw `gh api`.
- A stack waiver: name the CR whose gate validates the lower PRs (`waived -> CR-k`) and whether it passed; merging below before it passes leaves main with the failure if it fails.
- The restack after a merge is silent (no ask; none when the whole stack merged); the release CR's merge starts the release procedure. A complete stack whose top is the release PR: the same message asks the post-merge word (`help release-chief`).
