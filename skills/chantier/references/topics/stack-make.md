# Making the stack

- Once two CRs are handed back ready with PRs, and the stack can form (ordered, restacked, pushed, shipped, CI green at the top), create the native stack with the means your prompt names: the `gh stack` extension, or `$CHANTIER forge-stack create` when the user declined it (it retargets the PRs whose base is not the record's, then creates the stack; never a retarget by hand). Bottom to top, CRs not handed back ready on top as drafts. A means that is not available as named is an `anomaly` with the exact text: no other means without the user's word.
- Then, after the chain check, turn every PR of the mergeable part ready (`gh pr ready`) and record right after: `$CHANTIER stack --out-of-draft <cr>…`. On GitLab the means is always `forge-stack create` (the MRs of the mergeable part: `glab mr update <iid> --ready`, drafts on top; unproved).
- Any later change (insertion, restack after a merge, reorder) is `forge-stack rebuild`, after the rebases and pushes. A `rebuild` refused is an `anomaly` with the exact text, except when its error ends `stack #<n> is dissolved and no stack replaces it yet: run forge-stack create`: run `create` yourself. `the stack's state is unknown: run forge-stack show` stays an `anomaly`; you may run `show` and quote it.
- The five checks, by `$CHANTIER forge-stack show` (a line per failed check): the stack is open; holds every PR of the stack as it stands and no other; in `take stack` order; no ready-to-merge PR is a draft and every draft sits above them; the release PR, when in the stack, is on top. Drafts on top and `to come:` are no failure. On GitLab the checks read the chain (unproved).
