# The configuration and the team (part 1 of 3)

Nothing else is configured but the project's rules and `chantier.yaml`; every role runs the plugin's agent with its file's model unless the configuration says otherwise. Four layers, weakest to strongest: the plugin's `config/chantier.defaults.yml` (never edited); with an external planning surface, its root `chantier.yaml` (all its projects) and `projects/<name>/chantier.yaml`; then the code repository's `chantier.yaml` (`.yml` too, never both in one place). A layer carries only what it changes, merged node by node with the layers below it; `default` (or `~`, `null`; never empty, never quoted) takes a weaker layer's value back ("back to the plugin's agent" is `agent: default`). Every role setting is per host. Only the CLI reads, validates and resolves it; you edit a file, the code repository's or the surface's, only on the user's word, then `$CHANTIER playbook` to show the result (and its warnings). Keys: `hosts.<host>.roles.<role>.agent|model|skills|tools`, `long_gate.parallel` (1 when absent), `long_gate.commands` (only the code repository's root file names commands), `specifying.parallel` (4 by default), `batch.slots` (4 by default, 0 or more), `ci.beside_gate` (more CI minutes, spent on every approved round), `hosts.<host>.timing` (wakes, cache TTL, CI re-runs). A `beside_gate` or `timing` change counts from the next batch.
