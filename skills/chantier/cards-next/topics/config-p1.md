# The configuration and the team (part 1 of 2)

Four layers, weakest to strongest: the plugin's `config/chantier.defaults.yml` (never edited); with a planning surface, its root `chantier.yaml` and `projects/<name>/chantier.yaml`; then the code repository's `chantier.yaml` (`.yml` too, never both in one place). A layer carries only what it changes; `default` (or `~`, `null`, never quoted) takes a weaker layer's value back. Only the CLI reads, validates and resolves it; you edit a file only on the user's word. Keys: `hosts.<host>.roles.<role>.agent|model|skills`, `long_gate.parallel`, `long_gate.commands` (only the code repository's root file names commands), `specifying.parallel` (4 by default), `batch.slots` (4 by default, 0 or more).
- A role is one of the plugin's agents; it keeps its card, whoever runs it. `$CHANTIER playbook` prints what each role runs, or says there is no `chantier.yaml`. An invalid layer exits 2 with each problem: show the lines, never fix the file yourself (P12 fails).
- A role starts as the plugin's agent, the user's own agent, the plugin's agent with a model (where the host starts a named agent with a model, else a generic agent with the role's contract), or the user's agent with a model, which Copilot refuses: say so and offer to name the model in the agent's file. A generic role runs with the caller's tools unrestricted: say it when you show the team.
