# The spec critic

A fresh `spec-critic` reads the request, answers, specification and repository, and looks for a gap with the intent, an inconsistency, an unproved claim about the real world, a bundle. It never edits the specification, runs once per specification, never in a loop. A bundle is always a question, the split recommended: the parts are filed as new inbox items (`file`, each with its own title), the answer recorded, the writer's next run narrows the spec.
- Criterion (Chief of Staff and Griller alike): it runs on a CR that, wrong, would cost most: a role's contract, the CLI's refusals, a host behaviour, what the user sees or decides, an irreversible or shared step, several areas. Not on wording, a doc or a test alone. Subject and priority decide nothing; say why in the critic line. An automatable CR with no specification gets none. An item with no `Spec critic:` line is judged by whoever starts its writer, and the line is said with the start; a final specification gets none unless asked.
- Model: the playbook's. A user's word for another model for one run: start it through the host's model parameter; the project sets it in `chantier.yaml`. A host without it: say so, run the default, never a look-alike.
`help grill-critic-steps` for the steps.
