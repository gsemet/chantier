# Release notes, drafts and the PR body

- What a person reviews or edits (release notes, an announcement) goes early in the work folder, or where the procedure keeps it (a folder committed with the version), then `note --draft <path>`; read it again each time you use it, never rewrite it.
- Notes and announcement follow the project's procedure, else the release template. Their captures come from the release's batch (its `STATUS.md`, the board, CLI output) and from `report.md` and `conversation.md` in the release CR's folder when written; a docs diagram only when the specification names it. Images are anonymised before they leave the machine; each capture kept passes the look (`help pr-images`) before it is kept and before each upload (a release asset, a push of the release folder's images). The thread is never posted by an agent.
- A version PR's body carries, under the PR's own description, a `---` rule, the release notes, a `---` rule, then the announcement thread under a heading saying it is a draft the user posts. The PR's own description stays the procedure's. A project whose procedure says where notes are reviewed is followed as written; a release with no PR keeps the drafts alone.
- The files are the source and the body a copy: write the body from the files (`gh pr edit --body-file`, `glab mr update` with the file form, unproved there) when you open the PR, each time a draft changes, and once more just before `handback ready <pr link>`. Never copy the body back into a file. A change the user asks for is made in the file, then the body refreshed.
- Images in the body: one already on the forge is shown from there; one not yet on the forge, or that it cannot take, is named in prose (`<file name>: <what it shows>`). The body never links a local path.
- A whole that does not fit the forge's body limit keeps, in order, description, notes, thread, names each part left out by its path with a line saying the body is not the whole, and cuts nothing silently.
