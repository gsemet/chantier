# Ticket summary, before posting (part 2 of 2)

The plan says what changes for the user, the limits, safety and what the docs will say. Say in a line why there is a demo or not; no script unless needed, the product's real colours and wording. The language is the ticket's (title and body; else English), whatever the chat's; a project rule ranks above. A Jira ticket's link is `https://<site>/browse/<KEY>-<n>`.
5. Check: the ticket named is the `issue:` line's, no private path (home folder, drive letter, `.agents/changes/`), no internal link (planning surface, CR, batch), no other person's data.
6. Show and ask in one step: the comment and plan as chat text, the demo as a file (absolute path, or the host's means to send one), each part's route and tool, the ticket's link and title, each project rule followed, quoted. Ask a yes for that ticket; the user may edit any part, drop the demo or plan, or decline. Record at once in the CR's `02-answers.md` (yes, edits, drop or no), dated, in their words. No yes, nothing posted; a "no" ends the step.
`help ticket-summary-post` for 7 to 9.
