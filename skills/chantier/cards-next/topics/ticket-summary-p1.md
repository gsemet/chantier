# Ticket summary, before posting (part 1 of 2)

A CR with an `issue:` line has its reporter told what was accepted before any code; with none, skip the block (say so in a line only if asked). The Griller drafts, only the Chief of Staff posts. Steps:
1. When the user says it is grilled enough, in the turn of the spec-writer's start; offer a Griller's drafts when you next read the folder.
2. Can chantier write to that tracker? GitHub: `gh` reaching the issue; GitLab: `glab`; Jira or other: the project's rules say, else the capability the session has (MCP tool, CLI) provided it reads the ticket. None: skip and say in one line what is missing.
3. Read `$CHANTIER rules` for a tracker rule (access, key, closing keyword, language, template) and follow it.
4. Draft in `work/` (UTF-8, no BOM): `issue-comment.md` (accepted or not, the scope in two to five bullets, what is left out, "No date yet; the pull request will be linked here."; no CR number, batch, round, role, cost or `.agents/changes/` path), `issue-plan.md` (the decisions for an outside reader), `issue-demo.html` only when the change is visible and imitable (self-contained, no external resource, an HTML comment and a visible line saying it imitates the result). The ticket's language, English by default.
5. Check: the ticket named is the `issue:` line's, no private path, no internal link, no other person's data.
