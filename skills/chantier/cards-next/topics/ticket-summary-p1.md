# Ticket summary, before posting (part 1 of 2)

A CR with an `issue:` line has its reporter told what was accepted before any code; with none, skip the block (say so in a line only if asked). The Griller drafts, only the Chief of Staff posts. Steps:
1. When the user says it is grilled enough, in the turn of the spec-writer's start; offer a Griller's drafts when you next read the folder.
2. Can chantier write to that tracker? GitHub: `gh` reaching the issue (`gh issue view <link>`); GitLab: `glab` (`glab issue view <id>`); Jira or other: the project's rules say, else the capability the session has (MCP tool, CLI) provided it reads the ticket. None: skip and say in one line what is missing.
3. Read `$CHANTIER rules` for a tracker rule (access, key, closing keyword, language, template) and follow it; the defaults here apply only where it says nothing.
4. Draft in `work/` (UTF-8, no BOM): `issue-comment.md` (accepted or not, the scope in two to five bullets, what is left out, "No date yet; the pull request will be linked here.", one line linking a plan and demo posted apart, filled once posted; no CR number or slug, batch, round, role, cost, requirement ID or `.agents/changes/` path), `issue-plan.md` (the decisions for an outside reader), `issue-demo.html` only when the change is visible and imitable (self-contained, no external resource, an HTML comment and a visible line saying it imitates the result; not the batch's demo, which runs the real code).
