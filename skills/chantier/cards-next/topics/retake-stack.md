# A CR on another CR's branch

- In a stack batch the `base` that `take` prints may be another CR's branch (after a reorder it follows the new order): the nearest earlier CR that has a PR, handed back `ready`, that the forge does not show merged, or, for a CR with an open `after`, its highest open dependency's branch. Create the worktree on that base only, never on a branch with no PR, and open the PR on it as a draft. That branch is the stack driver's: never rebased by you but on a note or a `ship` refused `branch not based on`. A `base:` line after the `worktree:` line only explains the base; the worktree goes on the base the `worktree:` line names.
- `note rebase: stacked on <cr below>`: rebase onto that CR's branch (not the default branch), retarget your PR to it (`gh pr edit --base`, `glab mr update --target-branch`) while it is in no native stack, push, `ship` (`--conflict` by `help conflicts`). A series CR's PR opens as a draft on the base `take` printed: retarget nothing but on a `rebase:` note.
- A `ship` refused `branch not based on <cr>'s head` (your first `ship` included) means the CR below moved: rebase onto the branch the refusal names at once (in a series batch, the predecessor's), push, `ship` again; it is a move (`help conflicts`).
- Refused `<cr>'s branch moved since its last ship (<rec7> -> <tip7>)`: you are on its branch and it has not shipped its new head: do not rebase again; wait for its `ship`, then `ship` again.
- The forge shows the named CR merged but the record does not: once `status` shows it merged, `ship` again.
- `take` prints `; PR on <ref>` after the base: the place wins, rebase onto the place; the PR's base is the stack driver's (`forge-stack rebuild`) or yours on a `rebase: stacked on` note. `; PR base ? (not read …)` changes nothing for the rebase.
